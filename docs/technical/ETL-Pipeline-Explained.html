1. The whole pipeline on one page

ETL Extract, Transform, Load: take data out of one system, reshape it, and put it into another is the program that copies our consumer survey answers from Forsta into our database, and on to the portal and the team's inbox. It runs on its own: on each planned launch Monday it watches Forsta every 30 minutes until that week's wave is in, and every Friday it does one catch-all run.

SourceRespondents from a panel answer a survey in Forsta. When the target of about 400 qualified people is reached, the survey is closed.—
ExtractGets the list of every survey. Each survey is marked testing, due, loaded, failed, hibernated or too small. For each due survey it downloads the questionnaire and every response.etl/forsta_etl.py etl/forsta_client.py
TransformWorks out each question's type (single choice, tick-all, grid, number, text). Converts every answer from text to the right type. Removes or scrambles personal fields.etl/forsta_api.py etl/records.py
LoadWrites the survey, its questions, its respondents and their answers. Respondents and answers are written together, so they either all succeed or all fail. Any warning from the database fails the load instead of silently changing a value.etl/loaders.py app/core/database.py
VerifyChecks that the numbers of respondents, questions and answers match what Forsta sent. Only then does the wave appear in reports. The weekly run then compares every stored answer with Forsta, value by value, and runs the integrity checks.verify(), reconcile_survey() in etl/forsta_etl.py; etl/integrity.py

Then it emails and posts to the team.etl/run_pipeline.py app/data/ etl/serving.py api/dashboards.py etl/publish.py etl/notify.py
In one sentence
Every planned Monday evening the job starts asking Forsta "is this week's wave finished?" every 30 minutes. When it is, it downloads it in full, reshapes and stores it, proves nothing was lost, builds every finished number, publishes the portal's files and emails the team. A whole wave takes about 4–5.5 minutes end to end (section 14).

2. Where the data comes from: Forsta

Forsta the survey platform, formerly called Decipher, where Coresight's surveys are written, run and stored; our account is on the server se1.decipherinc.com holds every survey Coresight runs. Respondents never touch our systems; they answer in Forsta.

3. When it runs: frequency and timing

The job is started by launchd the macOS built-in scheduler, which runs a program at set times like cron on a server; if the Mac was asleep, it runs the missed slot when it wakes through the agent com.coresight.cip-forsta-etl, which runs scripts/weekly_forsta.py.

3.1 The schedule (India time, IST)

Since 23 Oct the job no longer runs at fixed times every day. It follows the data team's launch schedule the "Tracking by Week" tab of the team's workbook, imported into config/launch_schedule.yml: which Monday each lead sector and topic goes out.

WhenWhat happens
Planned Monday, 17:30A heads-up goes to Teams ("Forsta launches … today ~18:00 IST"). Then the watch one long-running job that repeats the normal run every 30 minutes starts: a run every 30 minutes until that week's wave is loaded and Forsta has closed it, for at most 54 hours (Mon 17:30 → Wed 23:30).
Friday, 09:00One catch-all run. It picks up annual and ad hoc studies, reopened surveys, and any wave the watch missed. Friday's run also always does the full integrity and drift checks.
HourlyA separate watchdog a small check that reads the job's "heartbeat" file and raises an alert if a run went silent, a planned Monday never started, or nothing has run for 8 days.

The schedule never runs out. The workbook's Mondays come first; after its last Monday, every Monday counts as a launch except dates listed under skip: in config/launch_schedule.yml (a holiday week, say), which an import of a new workbook keeps. launchd starts the job every Monday at 17:30; the job itself decides whether today is a planned launch. On a server the same two slots are Mon 12:00 and Fri 03:30 UTC (deploy/etl-loop.sh).

One run at a time
Every program that writes pipeline data (the scheduled run, a hand load, serving and cube rebuilds, publish, integrity repairs) takes the same run lock a named lock held in the database (GET_LOCK 'cip_etl'); a second writer finds it taken and stops politely instead of colliding. Two writers at once caused deadlocks on 20 Oct; this prevents it. The lock is held by a database connection, so a killed run frees it automatically, and the 54-hour watch keeps it alive with a tiny query every cycle.

So how fresh is the data?
Because the watch polls every 30 minutes, a weekly wave is usually loaded within half an hour of finishing. With the median of about 13 hours in field, the data typically lands on Tuesday morning IST.
Trackers only: Forsta sometimes leaves a full wave open (19 Oct: Midwest 80 of 85). So a weekly tracker counts as fielded fieldwork is over even though Forsta still says "live" once any of these holds: 9 hours since launch (about 03:00 IST), 400 qualified, or every quota cell full. It is then loaded, marked "in field", and reloaded in place when Forsta closes it. Annual and ad hoc studies never use this rule: they load only once Forsta closes them, so they are never published half-fielded.

4. The Forsta API: what we call

An API Application Programming Interface: web addresses that return data to programs instead of web pages to people is how we read Forsta. Ours is Forsta's REST a style of API where each address is a "resource" and you use standard web verbs such as GET to read it API, version 1.

4.1 Connection settings

SettingValue and meaning
Base URLhttps://se1.decipherinc.com/api/v1/. Every call starts with this. HTTPS means the traffic is encrypted.
MethodGET only. GET the web verb that only reads; POST, PUT and DELETE would create, change or delete, and our client does not contain them
AuthenticationHeader x-apikey: <key>. Header extra information sent with each request, alongside the address. Also sent: Accept: application/json and User-Agent: coresight-cip/1.0.
FormatJSON JavaScript Object Notation, a text format of names and values in {braces} and [lists], readable by people and programs
Timeout120 seconds per request (FORSTA_TIMEOUT_SECONDS). If Forsta does not answer in that time, the request is retried.
RetriesUp to 4 attempts, waiting longer each time, from 2 s up to 60 s (exponential back-off wait, then wait about twice as long before each new try, so a busy server gets breathing room). Retried on connection errors, timeouts, 429 and 5xx.
UsageForsta's x-usage-today header (calls used today) is written to the debug log.
Client codeetl/forsta_client.py, class ForstaClient

A run with nothing due makes 2 calls, plus one quota call per live survey. A run that loads one weekly wave makes about 6 calls: key, list, list again for the load, datamap, data, and data once more for the value-by-value check. The watch stops polling as soon as the week's wave is loaded and closed.

4.3 What Forsta's answers mean

Every reply carries an HTTP status code a three-digit number with every web reply: 2xx success, 4xx a problem with our request, 5xx a problem on the server:

CodeMeaningWhat the pipeline does
200OKCarries on.
401Key missing, wrong, revoked, or the user is disabledStops the run, exit 2. A person must renew the key.
403Key valid but no rights on this surveyThis wave fails and is recorded; the others continue.
428Survey hibernatedNever loaded. Left alone; reconciliation skips it with a warning.
429Too many requests (rate limit the server's cap on calls per period)Waits and retries, up to 4 attempts.
5xxForsta server errorRetries up to 4 times. If it still fails, the wave is marked failed and retried at the next run.

5. What data we receive

Forsta sends three kinds of JSON. Below is one real example of each; comments in yellow are ours.

5.1 The survey list: one item per survey

{ "path": "selfserve/58f/260908", // unique survey address "title": "Shopping and Spending - inc Home Furnishings + Holiday Tracker + GenAI", "state": "closed", // testing | live | closed "hibernated": false, // true = data not readable "tags": ["Coresight Research", "Weekly consumer tracker"], "createdOn": "2026-09-22T15:57:00Z", // Z = UTC time "dateLaunched": "2026-10-05T12:22:25Z", "closedDate": "2026-10-06T14:19:55Z", "qualified": 401, "total": 823, // finished & counted / everyone who started "sampleSources": ["114"] } // the respondent panel used

We use this to decide what to download. It is stored in the register table cip_forsta_survey. A register one row per Forsta survey recording what Forsta says about it and what the pipeline has done with it

5.2 The datamap: the questionnaire

{ "questions": [ { "qlabel": "q1", // question code "qtitle": "Which, if any, of these have you done in the past two weeks?", "type": "multiple", // single | multiple | number | float | text "grouping": "rows", "variables": [ // one per answer column in the data { "label": "q1r1", "rowTitle": "Met up with friends", "type": "multiple" }, { "label": "q1r2", "rowTitle": "Eaten at a restaurant", ... } ] }, { "qlabel": "D1", "qtitle": "What is your gender?", "type": "single", "values": [ {"value": 1, "title": "Male"}, {"value": 2, "title": "Female"}, ... ] }, { "qlabel": "qtime", ..., "flags": ["t"] } ] } // t = technical, v = virtual

A variable one column in Forsta's data; a single-choice question has one, a tick-all question has one per option (q1r1, q1r2…) is the unit we store answers against. Flags markers on a question: "t" technical (timings, status, conditions) and "v" virtual (values Forsta computes, e.g. device or browser) tell us which questions are not real survey questions.

5.3 The data: one object per respondent

[ { "record": "412", "uuid": "8k2f…", // Forsta's ids for this attempt "status": "3", // 3 = qualified "date": "10/05/2026 14:07", // completion, MM/DD/YYYY HH:MM "qtime": "611", // seconds taken "q1r1": "1", "q1r2": "0", // ticked / shown but not ticked "D1": "2", "D2": "34", "D8": "TX", // codes, numbers, text: ALL strings "q9oe": "Bought a new sofa", // open-ended text "RID": "…", "userAgent": "…", "url": "…", "session": "…", "dcua": "…" // personal: dropped or hashed }, ... ]
Important detail
Every value arrives as text, even numbers and codes ("3", "34"). Part of the transform is converting each value to its proper type. An empty value means the question was not asked or not answered.

6. Extract: finding and fetching surveys

What happens: the pipeline first lists everything, decides which surveys are ready, then downloads each ready one in full.

6.1 Step 1: discovery, on every run

Discovery the step that asks Forsta for the full survey list and updates the register; it downloads no answers calls rh/companies/all/surveys once and upserts "update or insert": change the row if it exists, add it if not, so running twice never creates duplicates one row per survey into cip_forsta_survey, keyed by the path. It then gives each survey a load state the pipeline's own label for a survey: testing, due, loaded, failed or hibernated:

For each survey in Forsta's list…
↓ Already loaded, and either still live or neither the close date nor the total changed?
Yes → loaded. Nothing to do (a tracker loaded while live is reloaded once Forsta closes it).
No ↓ continue
↓ Live, a weekly tracker, and fielded (9 h since launch, 400 qualified, or quota full; section 3.2)?
Yes → due (or failed if it failed last time)
No ↓ continue
↓ Is Forsta's state "closed"?
No (testing / live) → testing. Wait; never load an incomplete survey.
Yes ↓ continue
↓ Hibernated?
Yes → hibernated. Left alone. A person must reactivate it in Forsta.
No ↓
↓ Annual or ad hoc with fewer than 30 qualified?
Yes → too small. An aborted or test launch: never loaded.
No ↓
↓
Failed last time → failed (retried, up to 3 attempts)
Otherwise → due (load this run)

Reopened surveys: if a loaded survey's close date or total changes (it was reopened and more people answered), it becomes due again and is reloaded in place.

Every change of state is also written to a history table, cip_forsta_event, and each live survey's quota progress to the register, for the portal's Launch schedule page.

Discovery also records study_type: tracker if the survey is tagged "Weekly consumer tracker" or titled "Shopping and spending…", annual if tagged "annual tracker", otherwise adhoc. In the same step it rebuilds the survey calendar (section 10).

6.2 Step 2: choose what to load

All due surveys, and failed ones with fewer than 3 attempts, are taken oldest close date first and loaded one at a time. If one fails, its error is saved in last_error and the run moves on to the next. One bad survey never blocks the others. A survey that has failed 3 times in a row waits for a person to run it by hand (section 12), instead of a full download every 30 minutes.

8. Load: writing to the database

What happens: the transformed wave is written into cip_stg in a fixed order. The step that replaces respondents and answers is a single transaction a group of database writes that either all succeed together or are all undone together, so nobody ever sees half a wave.

1Survey row in cip_survey, set to load_status = loading (not visible in reports).
↓
2Run log row in cip_load_log, with source_ref = forsta:{path}. This is the audit trail of every run. Load log a diary of every load: what, when, rows read and rows written, success or error
↓
3Definitions: topics, questions, options, items and fields (cip_topic, cip_question, cip_option, cip_item, cip_field). One batched statement per table.
↓
4Transaction A, all or nothing:
a) upsert every respondent into cip_respondent, keyed by survey + record;
b) delete respondents Forsta no longer sends, with their answers, profile and cohort rows;
c) delete the wave's old answers, then upload the new ones in one LOAD DATA MySQL's bulk loader: the rows travel as one compact tab-separated file instead of thousands of INSERT statements statement. If the database reports any warning at all, even a mild "note", the whole transaction is undone and the wave fails: a value is never silently changed.
↓
5Verify (section 9). If anything is off, the wave is marked failed.
↓
6Tidy the answer list: an answer row the questionnaire no longer lists and nobody chose is removed (8.2).
↓
7–13Derive: profiles, question bases, concepts, cohorts and cube, search, line-by-line, serving rows (section 10).
↓
14–16Finish: log row closed with row counts. cip_survey.load_status = verified, register set to loaded, calendar rebuilt, and next week's and next year's waves refreshed so they compare with this one.

8.1 Why it is safe to run again and again

Idempotent
Idempotent running the same load twice gives exactly the same result as running it once. Every write is an upsert or a replace keyed on Forsta's own ids (path, uuid, record, variable label), so nothing is ever duplicated.
No half-loaded waves
If transaction A fails, the previous answers are untouched. A wave that was already verified stays visible with its old, correct data.
Why one bulk upload?
Each database call from India to Azure takes about 250 ms. Writing 145,000 answers one by one would take 10 hours. One LOAD DATA upload sends them all at once; the whole write step on 23 Oct (693 respondents and 128,665 answers) took 20.6 s. The upload file is temporary and deleted straight away. If the server refuses bulk uploads, the loader falls back to batches of 5,000 rows.

8.2 What changed in the load since 14 Oct

ChangeWhy it matters
Decimals rounded to 4 placesMySQL stores 4 decimals. A longer value (a Forsta timing like qtime on 20 Oct) used to make the database round it with a warning, and the strict warning gate would then fail the whole wave on every attempt. Rounding first means a long decimal no longer fails a wave.
Strict warning gateAny LOAD DATA warning undoes the write. Better a loud failure than a quietly altered number.
Unlisted, unchosen answers removed (drop_unlisted_items)Definitions are only ever added or updated, never deleted. So when a questionnaire's answer list is corrected, the old rows used to linger as empty duplicates ("YouTube 0 %" next to "YouTube 47 %"). After the answers are written, a row the questionnaire no longer lists and that nobody chose (no code other than 0, no number, no text) is deleted with its "not chosen" zeros. A row with real answers is always kept. Both loaders (Forsta and legacy) do this.
Legacy relabel (surveys 97 and 201)In two old waves the answer ids had shifted: SurveyMonkey survey 97 (US Social Commerce 2023) filed Facebook's 818 picks under "LinkedIn", and Qualtrics survey 201 (tracker, 15 Aug 2022) had 88 shifted grocery-retailer answers covering 8,029 picks. The legacy loader now gives each answer the one text its respondents actually saw. A scan of all 287 legacy waves found nothing else. After the reload, survey 97's Q7 shows Facebook 818 (63.3 %) and YouTube 612 (47.3 %).
Failed reload drops its serving rowsIf a reload fails after its write, that wave's serving rows are removed, so no screen or published file keeps numbers for answers that have changed (section 12).

9.1 Two gates since 23 Oct: the count, then every value

The count gate above proves nothing was lost. It cannot see a value that was stored wrong. So once a wave is in, the weekly run downloads its data from Forsta a second time and compares every stored answer with Forsta, value by value: codes exactly, numbers to 4 decimals, texts exactly. It costs one more download of the wave from Forsta.

ResultWhat the run does
All answers equalNothing; the wave stays published.
Some answers differCounted as an integrity problem: alert "integrity check: N problems" with the first differences.
Nothing could be checked (checked == 0, e.g. Forsta unavailable or hibernated)Also a problem, never a silent pass. The same rule applies to python -m etl.forsta_etl --reconcile.

10. Derive: making it report-ready, publishing, telling the team

What happens: after verification, everything a report needs is calculated once, at load time, so the portal and exports only read finished numbers. Then the portal's files are published and the team is told.

Output (table)What it is and how it is built
Profile
cip_profile		One row per respondent with their demographics, read from D1 gender, D2 age, D3 relationship, D4 ethnicity, D5 income, D6 urban/suburban/rural, D7 politics, D8 state, CS1/CS2 outlook. Adds:
• Age band: 18-29 · 30-44 · 45-60 · Over 60 ("Under 18" is not banded)

cip_question.base_n		Base the number of people a percentage is calculated over: qualified respondents who were shown the question
Concepts
cip_concept*		Concept "the same question" across waves and platforms, matched by wording because Forsta codes such as D2 or BT14 change meaning between waves. Same wording and options → confirmed automatically. Changed options, or wording at least 85% similar → proposed for a person to confirm. Otherwise → a new concept. A one-off command (python -m app.data.harmonise --confirm-same-wording) also confirms waiting proposals whose wording and type exactly match their concept, when no other question in the wave uses it (1,322 units in the 23 Oct dry run); similar-wording proposals still wait for a person. Search
cip_search		A full-text index of wave titles, question wording and concepts, so "GLP-1" finds every wave that asked about it.

cip_tracker_line		The data team's "Weekly Line-By-Line Survey Data" sheet, rebuilt automatically: one row per qualified respondent in the team's column order. Checked against the team's file across 16 waves: identical apart from 3 errors in the team's file.

cip_wave_module		Which sector, topics and seasonal trackers each wave carried, plus the holiday-season wave number. This enables "wave N vs last year's wave N" and predicts the next 12 lead sectors.
Serving rows
srv_wave, srv_result, srv_answer		The finished rows every screen reads, one per cube cell: labels, percentage, prior week and same week last year, and warning flags (small base under 50, wording changed, base shifted by more than 10 points). Rules since 23 Oct:
• Cells are keyed by item and option id, not by label, so two answers that share a label ("Other", or survey 97's two "YouTube" rows) are both served.
• Prior and last year are matched through the harmonised concept first, then by question code + normalised label + option code, and only when that match is unique in both waves.
• Significance flags sig_prior / sig_ly: a two-proportion z-test a standard test of whether two percentages differ by more than chance, here this week vs prior week (or last year) on each Total row, then Benjamini–Hochberg at 5 % FDR a correction for testing hundreds of answers at once: it keeps the expected share of false "significant" calls at 5 % over the wave's testable Total rows only. Testable means both percentages exist, both bases are at least 30, the base did not shift, and the answer is not a filler ("None of these", "Other –", "Prefer not…").
• No blank segments: respondents whose wave never asked a demographic are not shown as a segment equal to Total.
• Excluded waves (test runs and aborted launches listed under exclude: in config/survey_map.yml) and non-tracker waves under 30 qualified get no serving rows: their raw data stays, but no screen lists them.
• Annual studies compare with their family's latest wave 300–430 days earlier (the family map), since they are not fielded in the same week each year.
• A tracker wave loaded while Forsta still had it open is marked in field until the reload after close.
DependantsNext week's wave and next year's same wave are rebuilt, so they now compare with this one.
Topic dashboards
cip_dash_*		The 19 configured dashboards (config/dashboards.yml: holiday tracker, tariffs and inflation, GenAI, GLP-1, financial health, sector modules…) are rebuilt for the new waves that carry their module. A takeaway calls a change significant only when the serving row carries the sig_* flag.

12. When something goes wrong

Every run ends with an exit code, written to the log, that says how it went:

CodeMeaningWhat to do
0Everything due loaded and verified, or nothing was dueNothing
1A wave failed to load or verifyRead cip_forsta_survey.last_error (also in the alert). The next runs retry it automatically, up to 3 attempts.
2Forsta rejected the key, the key is missing, or the database schema is older than the codeRenew the key in .env, or run python scripts/init_db.py
3Loaded fine, but an already-published number changedReview on the Publications page
4Database unreachable after 4 tries over 15 minutesCheck the VPN or the Azure firewall (the office IP changed on 13 Oct). The next slot retries; during a Monday watch, the next 30-minute cycle.
5Loaded fine, but an integrity check (or the value-by-value comparison) found something it could not repairRead the "integrity check: N problems" alert; it lists each problem.

12.1 Safety nets added since 14 Oct

If……then
One watch cycle crashes (Forsta down past its retries, the database dropping mid-run)The crash is logged and alerted ("a watch cycle crashed"), and the watch carries on 30 minutes later. Before, one crash ended the Monday watch and the wave waited for Friday.
The run stops without finishing (killed, Mac asleep or restarted)The hourly watchdog sees the missed heartbeat and alerts; it also alerts if a planned Monday never started, or nothing has run for 8 days.
Something goes wrongAn alert by email and Teams, with the problem count in the subject ("integrity check: 3 problems", "published numbers moved in 2 publications"), so a new problem is told at once rather than after the 6-hour repeat window.
A reload fails after its writeThat wave's serving rows are dropped and the portal is republished, so no screen or published file shows numbers for answers that have changed. A reload that fails before its write leaves the old, verified wave untouched.
A publish fails (a gate or a crash)Its build folder is removed and the previous version stays live. It can never become a rollback target.
A published version turns out wrongpython -m etl.publish --rollback points current back to the previous version (the last 3 are kept).
A second writer starts while a run is goingIt finds the run lock taken and stops (section 3.1).

14.3 A caveat about the cube

Tonight's cube time is not the usual one
The cube step took 27–42 s on 20–22 Oct. Tonight it measured about 110 s, three times, with unchanged code, right after a full rebuild of all waves.
